# PostgreSQL Schema Reference

This is the PostgreSQL schema the committee service will move its state to (see the storage
migration epic, [lfx-self-serve-ops#1133](https://github.com/linuxfoundation/lfx-self-serve-ops/issues/1133)).
**Nothing reads or writes it yet**: NATS KV is still the only store, and the service runs unchanged
with no database configured. The store implementation, the dual-write modes and the backfill land in
follow-up tickets. For what is stored in NATS today see [nats-storage.md](nats-storage.md).

Sources of truth:

- Migrations: `internal/infrastructure/postgres/migrations/` (embedded into the binary)
- Runner: `internal/infrastructure/postgres/migrate.go`
- Tests: `internal/infrastructure/postgres/migrate_test.go`

## Tables

| Table | Replaces (NATS KV bucket) |
| --- | --- |
| `committees` | `committees` |
| `committee_settings` | `committee-settings` (`writers` and `auditors` are JSONB columns on this row) |
| `committee_members` | `committee-members` |
| `committee_invites` | `committee-invites` (adds `updated_at`) |
| `committee_applications` | `committee-applications` (adds `updated_at`) |
| `committee_link_folders` | `committee-folders` |
| `committee_links` | `committee-links` |
| `committee_documents` | `committee-documents-metadata` (file bytes stay in the NATS Object Store) |
| `group_weekly_briefs` | `group-weekly-briefs` and `group-weekly-brief-uid-index` |
| `group_weekly_brief_throttle` | `group-weekly-brief-throttle` |

Every table has a `revision` column fed by the shared sequence `committee_revision_seq`. It is the
optimistic-concurrency token the API exposes as `revision` / `etag` / `if_match`. While both stores are
written the composite store sets it from the KV revision; when PostgreSQL becomes the authority the
sequence must first be advanced above the highest KV revision so a stale pre-cutover token can never
match.

Design choices made so a backfill from KV cannot fail on existing data: ids are `TEXT`, there are no
`CHECK` constraints on enum-like columns, dates the Go models keep as strings stay `TEXT`, and there
are no foreign keys (KV has no referential integrity). Foreign keys are added later as `NOT VALID`
and validated once the planned `verify` command ([#1198](https://github.com/linuxfoundation/lfx-self-serve-ops/issues/1198))
reports no orphans. Deletes are hard deletes.

## Unique indexes: the KV lookup keys

The `lookup/...` keys in NATS become unique indexes. Each reproduces the normalization of the key it
replaces (the `BuildIndexKey` methods in `internal/domain/model`), so a record KV accepts is accepted
here and a duplicate KV rejects is rejected here.

| Unique index | KV lookup key | Normalization |
| --- | --- | --- |
| `committees_project_name_key` | `lookup/committees/<hash>` | `(project_uid, name)`, case-sensitive |
| `committees_sso_group_name_key` | `lookup/committee-sso-groups/<name>` | exact name, only where it is not empty |
| `committee_members_committee_email_key` | `lookup/committee-members/<hash>` | committee, email trimmed and lowercased |
| `committee_invites_committee_email_key` | `lookup/committee-invites/<hash>` | committee, email trimmed and lowercased |
| `committee_applications_committee_email_key` | `lookup/committee-applications/<hash>` | committee, email trimmed and lowercased |
| `committee_link_folders_committee_name_key` | `lookup/committee-folders/<hash>` | `(committee_uid, name)`, case-sensitive |
| `committee_documents_committee_name_key` | `lookup/committee-documents/<hash>` | `(committee_uid, name)`, case-sensitive |
| `group_weekly_briefs_committee_window_key` | `group-weekly-brief-uid-index` | committee and the UTC date of the window start |
| `group_weekly_brief_throttle_committee_window_key` | `group-weekly-brief-throttle` key | committee and the UTC date of the window start |

The four member secondary indexes (`lookup/committee-members-by-*`) become ordinary indexes on
`committee_members`: `committee_uid`, `organization_id`, the normalized email, and the normalized
username.

Emails and usernames are normalized with `committee_normalize_key()`, a function that reproduces Go's
`strings.TrimSpace(strings.ToLower(x))`. PostgreSQL's own `btrim(x)` strips only ASCII spaces, whereas
Go also strips tabs, newlines and no-break spaces, so the function lists the same characters as Go's
`unicode.IsSpace`. A test compares it against Go directly.

Residual differences from the KV keys:

- The KV keys also lowercase and trim `committee_uid`. Committee UIDs are lowercase UUIDs generated by
  the service, so the unique indexes use `committee_uid` as stored.
- `lower()` follows the database locale. The Turkic locales (`tr`, `az`) lowercase `I` to a dotless `i`,
  which Go does not, so the function maps `I` and the dotted capital `I` (U+0130) to `i` first and the
  result does not depend on the locale. Every other character uses the database's simple per-character
  case mapping, which matches Go on a database that uses the **libc locale provider** with a UTF-8
  locale (the default, and the RDS default) apart from rare characters whose case differs between
  Unicode versions. Two kinds of database do not match: a `C`/`POSIX` one folds ASCII only, and one
  created with the **ICU provider** applies contextual casing (for example the final sigma: ICU
  lowercases `ΟΣ` to `ος`, Go to `οσ`). Create the database with the libc provider and a UTF-8 locale;
  a test checks that case against Go. If exact parity for every character is ever needed, the store can
  compute the key in Go and store it in a column the database only enforces uniqueness on.

## Data classification

Personal data and credentials are marked on the columns themselves, so tooling can read the marking
from `col_description()` instead of relying on a comment in the SQL:

- `committee_settings.chat_webhook_url` is marked `SENSITIVE`. It is a bearer credential (anyone holding
  the URL can post to the committee's chat channel), the service never returns it or indexes it, and
  nothing that exports these tables (the warehouse pipeline, backups shared outside the service, ad-hoc
  queries) may include it. The schema does not enforce that exclusion yet; the store and the dbt tickets
  must (an export role without access to the column, or a separate table).
- Columns holding personal data are marked `PII`: member and applicant names, emails, usernames, avatars
  and profiles, invite and application free text, the `inviter`, `created_by` / `updated_by` and
  `last_edited_by` users, the `writers` / `auditors` lists, the committee `charter` (it records who
  last updated it), and the weekly brief `brief_text` and `source_refs` (member roster changes name members). A test fails when a marker is removed.

## Migrations

Migrations use [goose](https://github.com/pressly/goose), embedded with `go:embed`, and run through
`postgres.Migrate`. A session-level advisory lock lets one process migrate while others wait, and
each migration runs in its own transaction, so a failure leaves the schema at the last completed
version.

Rules for adding a migration:

- Keep it **additive** (new tables, columns, indexes). The previous release keeps running against the
  shared database while a new one migrates it, so a migration must not break the old code.
- Give it a `-- +goose Down` section that reverses it exactly. The tests apply every down and up.
- Once a table holds data, build indexes with `CREATE INDEX CONCURRENTLY` in a migration marked
  `-- +goose NO TRANSACTION`; a plain `CREATE INDEX` is only safe on the empty tables of the first
  migrations.
- Mark new personal data columns `PII` and credentials `SENSITIVE` with `COMMENT ON COLUMN`.
- Reproduce KV semantics, not an idealized schema: change a constraint here only together with the
  service behavior that depends on it.

## Connecting

PostgreSQL is behind a feature flag, `POSTGRES_ENABLED` (default off; only the exact value `true` enables it). With the
flag off the service never connects, even if `POSTGRES_URL` is set, so deployments are unchanged until it is turned on
(see the PostgreSQL table in [cmd/committee-api/README.md](../cmd/committee-api/README.md)).

With the flag on, at startup the service opens a `pgxpool` pool, pings the database, and runs `postgres.Migrate`
(a session advisory lock keeps replicas starting together from racing). Nothing reads or writes the data yet, so
PostgreSQL must not be able to take the service down: a missing URL, bad `POSTGRES_MAX_CONNS`, an unreachable
database or a failed migration is logged as an error and the service keeps running without it. Once the service
depends on the database (the dual-write and PostgreSQL modes), that choice has to be revisited per mode.

- The URL carries a password, so it is never logged and never appears in an error: `postgres.NewPool` removes the
  password (URL form, keyword form and `password=` query parameter) from everything it returns, and the startup log line
  uses `postgres.RedactURL`.
- `/readyz` also pings PostgreSQL only when `POSTGRES_READINESS_CHECK=true`. Keep it off until the service depends on the
  database, so a database outage does not take pods out of rotation. A failing check returns a generic 503 and logs the
  cause, and if PostgreSQL is enabled but could not be set up the check reports not ready.
- Use `sslmode=verify-full` (with `sslrootcert`) outside local development: `require` encrypts but does not verify the
  server certificate, and the driver default `prefer` can fall back to plaintext.
- The service applies the migrations itself at startup, so the role in `POSTGRES_URL` needs DDL rights. Before the
  service serves real traffic from this database, move the migrations to a separate role (a Job or init container) and
  give the runtime role DML only.

## Store

`postgres.Store` (`internal/infrastructure/postgres`) is the PostgreSQL implementation of the committee storage ports,
added one port at a time. It is not selected by the service yet; the composite store (#1197) does that. It covers the
committee base and settings (create, get, list, find by project and name, update, update settings, delete, and the
`has_mailing_list` and `total_members` counters) and members (create, get, update, delete, and the by-committee,
by-organization, by-email and by-username listings).
Invites (create, get, update, list) and applications (create, get, update, delete, list) follow the same rules.
Links and link folders (create, get, update, delete, list) follow them too.
Document metadata (create, get, update, delete, name check, list) does too.
Weekly briefs and their throttle entries (get by window, put, index keys) follow the KV semantics described below.

- **Duplicates come from the schema.** The store does not check names itself. A violation of
  `committees_project_name_key`, `committees_sso_group_name_key` or a primary key becomes `errs.Conflict` (the SSO one
  wraps `errs.ErrSSOGroupNameTaken`), so the HTTP mapping is the same as with KV.
- **Revision is the concurrency token.** It is assigned from `committee_revision_seq` on insert and replaced on every
  update. An update or delete whose revision is stale matches no row and returns `errs.Conflict`, the error the service
  returns today when it finds the revision has moved; a missing record is `errs.NotFound`. The check is a single
  `UPDATE ... WHERE revision = $n`, so two writers with the same token cannot both win.
- **Multi-row operations are one transaction.** Creating a committee with settings, and deleting a committee with its
  settings, commit or roll back together. A failed create leaves nothing behind, with no lookup keys to clean up.
- **JSONB lists read back like KV.** `scope`, `deliverables`, `key_dates` and `external_sources` are `omitempty` in the
  KV record, so an empty list is stored as `[]` and read as `nil`. `writers` and `auditors` are not `omitempty`, and the
  service tells "not set" from "set to empty", so they keep the difference: `nil` is stored as JSON `null` and an empty
  list as `[]`.
- **Timestamps** come back in UTC and truncated to microseconds, the precision of `TIMESTAMPTZ`; KV keeps nanoseconds
  and the writer's zone. Comparisons between the stores (the composite store, `verify`) must normalise the same way.
- **Member lookups use the schema's indexes.** A member's email is unique per committee after the trim and lowercase
  that `committee_normalize_key` applies, so `First.Last@Example.com` and ` first.last@example.com ` are the same
  member. The by-email and by-username listings compare through the same function. The KV by-organization index is keyed
  by the 18-character form of the Salesforce account ID, so a member stored with the 15-character form is listed under
  either spelling: the query matches the 18-character form and its 15-character prefix.
- **Invites and applications** have the same per-committee unique email as members, so an email that was invited or
  applied from once is a conflict whatever the case, spacing or status of the first record. The model has no update
  time, so `updated_at` is the creation time on insert and the current time on every update, and is not read back.
  An invite with no expiry is stored as `NULL`. `UpdateInvite` checks a changed email against the unique index, where
  KV keeps the lookup key of the email the invite was created with. `DeleteApplication` is not an error when the
  application is already gone, as in KV, where the committee cascade may have removed it.
- **Links and folders** are found by uid within their committee: a record of another committee is `errs.NotFound` for
  get and delete, as in KV. Links have no unique name; a folder name is unique per committee and case-sensitive, so
  `Legal` and `legal` can both exist. Deleting a folder leaves its links alone (no foreign key, as in KV). `UpdateLinkFolder`
  checks a changed name against the unique index, where KV keeps the lookup key of the name the folder was created with.
  `UpdateLink` and `UpdateLinkFolder` find the record by uid and revision alone, as KV does, so they are for the
  audit-sync tooling, not for a request path that must keep a record in its committee. `ListAllLinks` and
  `ListAllLinkFolders` return every record when the committee is empty.
- **Document metadata** is found by uid within its committee for get and delete, like links; `UpdateDocumentMetadata`
  matches on the uid and revision alone, as KV does, for the audit-sync tooling. A document name is unique per committee and
  case-sensitive, and `UpdateDocumentMetadata` checks a changed name against the unique index, where KV keeps the lookup
  key of the original name. `DocumentNameExists` is the same query the unique index answers. The file bytes stay in the
  NATS Object Store, keyed by the document uid: the store implements no file method (`GetDocumentFile`, `PutDocumentFile`,
  `DeleteDocumentFile`), so the composite store keeps calling the object store and deletes the file after the metadata.
- **Weekly briefs and throttle entries** are found by committee and the UTC day of `window_start`, the KV key
  `<committee_uid>.<yyyymmdd>`, whatever time zone the connection uses (the queries use the same
  `(window_start AT TIME ZONE 'UTC')::date` as the unique indexes). A put with a revision is a compare-and-swap and
  without one replaces the brief with the same uid, as in KV, and a lost swap is `errs.ServiceUnavailable`, the error KV
  returns; the throttle works the same way (revision 0 creates). Edits re-read and answer a lost swap with a revision
  mismatch, and generation is redelivered, but `Claim`, which inserts a new brief, returns it to the HTTP client.
  Differences from KV: a window holds one brief, so a second brief with another uid for the same window is that same
  retryable error, where KV lets it take over the index entry and orphans the first (`Claim` may then answer 503 after
  it has charged the throttle); `window_end` keeps microseconds, so the last
  nanosecond of the week (`23:59:59.999999999`) reads back as `23:59:59.999999`, still the same week. The throttle
  entry is returned as JSON for the brief's window, and a failed throttle lookup is logged and leaves it out, as in KV.
  `ListGroupWeeklyBriefIndexKeys` rebuilds the KV keys, with `/`, `:` and spaces replaced by dots as KV does (the
  replacer is repeated from the NATS adapter, so change both together). A put finds the brief by uid and writes the
  committee and window it is given, as KV does: the composite store must take the uid from a lookup by committee and
  window, never from a request. Revisions come from the shared sequence, not a bucket's, so a revision a client holds
  across the switch from KV gets one revision mismatch.
- **Whole-table reads stream.** `EachMember` and `EachMemberStrict` read rows one at a time and stop at the first error
  `fn` returns, so a full scan does not hold every member in memory. `ListAllMembers` still returns a slice because the
  port does; prefer `EachMember` for the whole table. A call back into the store from `fn` uses a second connection.
- **Explicit revisions** let the composite store (#1197) carry the KV revision into a row in `dual` mode.
  `postgres.WithRevision(ctx, rev)` makes every create or update made with the returned context leave `rev` as the
  record's revision instead of a value from `committee_revision_seq`; it works for every record and for the counter
  updates. Derive a fresh context from the plain parent for each store call: a context reused for a second write
  stamps the same revision on another record. A committee create writes two rows, so `WithSettingsRevision` sets the
  settings row's revision (`WithRevision` sets the committee's). The guard is unchanged: an update or delete is still
  matched against the revision the caller read, so a stale token is rejected whether or not a new revision is given.
  An update rejects (`errs.Validation`) an explicit revision that is not above the one it replaces, because the same
  or a lower value would keep a token that was already handed out valid for the new content; the counter updates
  check against the committee's current revision, in Go and in the statement. A revision of 0 or above the range of
  the column is an error. In `dual` mode every write must carry its revision: a write without one takes a sequence
  value that can equal a KV revision a stale client still holds, unless the sequence was also advanced before `dual`
  started. At the flip from KV to PostgreSQL, call `Store.AdvanceRevisionSequence(ctx, highest)` with the highest
  revision over **every** KV bucket the tables mirror (KV revisions are stream sequences counted per bucket, while
  all tables share this one sequence): the sequence then issues only values above it, so a token from before the flip
  can never match a revision issued after it, and a lower value never lowers the sequence. Call it while no writes
  are in flight, because the read and the set are not one atomic step. Rolling back from PostgreSQL to KV, and
  invalidating the tokens issued in between, is the composite store's to define: it needs no primitive here.

## Running the tests

The schema tests need a real PostgreSQL. Point `TEST_DATABASE_URL` at a database the tests may modify
(each test works in its own schema and drops it afterwards):

```bash
docker run -d --rm --name committee-pg -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_DB=committee_test -p 127.0.0.1:5432:5432 postgres:16-alpine
until docker exec committee-pg pg_isready -h 127.0.0.1 -U postgres -d committee_test >/dev/null 2>&1; do sleep 1; done
TEST_DATABASE_URL='postgres://postgres@127.0.0.1:5432/committee_test?sslmode=disable' make test
```

Without `TEST_DATABASE_URL` the PostgreSQL tests are skipped locally. On CI (`CI` is set) a missing
`TEST_DATABASE_URL` fails the tests, and the build workflow provides a PostgreSQL service.
